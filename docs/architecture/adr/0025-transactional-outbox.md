# ADR 0025: Transactional Outbox

- Status: Accepted
- Date: 2026-08-23 (documents behavior implemented and proven end to
  end during Phase 0C; written retroactively during Phase 0C.3A to
  close a dangling reference — see "Note on this ADR's timing" below)

## Context

ADR 0010 established that School OS uses Laravel's in-process event
system, not a distributed broker, for domain events. That decision left
one problem unsolved: a naive `DB::transaction(fn () => { ...write
state...; event(new SomethingHappened(...)); })` followed by
`Event::dispatch()` firing a QUEUED listener has a real crash window —
if the process dies between the transaction committing and the queue
job actually being pushed (or if the queue push itself fails), the
business state change is durable but the event that was supposed to
notify every other module about it silently never happened. For a
School ERP, this is not an acceptable failure mode: a fee payment
being recorded without its `PaymentReceived` event ever reaching a
receipt-notification consumer, or a student admission without its
`StudentAdmitted` event ever reaching the class-roster consumer, is
exactly the kind of "worked in dev, silently dropped a critical side
effect in production" bug this architecture must design out from the
first module that uses it, not retrofit later.

## Decision

**Every domain event is recorded into a durable outbox table
(`domain_event_outbox`) inside the SAME database transaction as the
business state change that produced it**, via
`App\Listeners\RecordDomainEventToOutbox` — registered against the
`App\Support\Events\ShouldBeOutboxed` interface (Laravel's own
interface-listener auto-discovery, so any event implementing it is
outboxed with zero additional wiring) and invoked **synchronously**,
not queued: `event()` is called from inside the caller's own
`DB::transaction()`, so `RecordDomainEventToOutbox`'s `INSERT` shares
that exact transaction and connection. If the transaction later rolls
back, the outbox row rolls back with it — the event genuinely never
existed. If the transaction commits, the outbox row is durable,
independent of whatever happens next (a queue outage, a crashed
worker, a network partition) — proven in
`tests/Feature/Events/OutboxTransactionalityTest.php`'s two directly
complementary tests (`a_committed_transaction_leaves_the_event_durably_
in_the_outbox` / `a_rolled_back_transaction_leaves_no_event_behind`).

**Event envelope** (mirrored as JSON Schema in
`packages/contracts/events/`, full field table in
`docs/architecture/EVENTS.md`): `eventId` (`domain_event_outbox.id`,
UUIDv7, generated by the event class before the row is created — see
`App\Support\Events\OutboxedEventDefaults`), `eventType`, `eventVersion`,
`occurredAt`, `schoolId`/`campusId` (tenant identity), `actorId`
(nullable — system-triggered events may have none), `requestId`/
`correlationId`/`causationId` (see "Correlation and causation" below),
`payload` (event-specific, deliberately minimal — references and
facts, never a full denormalized record).

**Dispatch model**: `App\Console\Commands\DispatchOutboxEvents`
(`platform:outbox-dispatch`) claims a bounded batch of `pending` rows
via `SELECT ... FOR UPDATE SKIP LOCKED` (native Postgres row locking —
proven safe for concurrent dispatcher runs in the pre-existing
dispatcher concurrency test), marks each `dispatched` (with
`attempts + 1` and `dispatched_at`), and pushes
`App\Jobs\ProcessOutboxEventJob::dispatch($id)->onQueue('default')
->afterCommit()` — the DB status update and the queue push happen in
the SAME transaction, and Laravel only actually pushes to the queue
driver after that transaction commits, so a mid-transaction crash never
leaves a "dispatched but not actually queued" or "queued but not
marked dispatched" row.

**Queue boundary**: `ProcessOutboxEventJob` is where the outbox pattern
hands off to Laravel's ordinary queued-job infrastructure (ADR 0006).
It establishes its OWN tenant context from the event's own
`school_id`/`request_id`/`correlation_id` (never inherited from
whatever dispatched it — the dispatcher is an inherently cross-School
process, see "Tenant safety of the outbox" below), then runs every
registered `App\Support\Events\EventConsumer` whose `handles($eventType)`
matches, through `IdempotentConsumerGuard`. One consumer's failure does
not block sibling consumers for the same event (failures are collected
and re-thrown together after the loop, so the job still fails and
Laravel retries it — safe, because already-succeeded consumers are
already receipted and no-op on the next attempt).

**Idempotent consumer receipts**: `event_consumer_receipts` — a
database `UNIQUE(consumer_name, event_id)` constraint is the
AUTHORITATIVE deduplication mechanism (not an existence-check
pre-condition alone), enforced by
`App\Support\Events\IdempotentConsumerGuard`: the consumer's side
effect and its receipt are written in the SAME transaction, so a
worker race either has exactly one winner (the loser's whole
transaction — side effect included — rolls back on the unique
violation) or, on a crash before commit, nothing persisted at all.
There is no window where a side effect persists without its receipt or
vice versa. Proven end to end, including explicit redelivery, in
`tests/Feature/Events/EndToEndProofATest.php` and
`tests/Feature/Webhooks/EndToEndProofBTest.php`'s duplicate-event
tests.

**Correlation and causation**: `correlationId` propagates from the
original triggering request's `TenantContext` (falling back to the
event's own id if the request never set one) all the way through
outbox → dispatch → consumer → any consumer-triggered side effect
(notification, webhook delivery) — proven by
`EndToEndProofATest`'s assertion that a `Notification` row's
`correlation_id` matches its triggering event's. `causationId` (which
prior event, if any, caused this one) exists in the envelope for a
future chain-of-events scenario no current consumer produces yet.

## Tenant safety of the outbox

`domain_event_outbox` and `event_consumer_receipts` are deliberately
**central/platform tables, not RLS-protected** — the one explicit,
reviewed exception to ADR 0004's "every tenant-owned table is
RLS-protected" rule, and only because these two tables are not
tenant-owned data in the same sense a School's settings or webhook
endpoints are. The outbox dispatcher (`DispatchOutboxEvents`) is
inherently a cross-School background process: it must see pending
events for every School to dispatch them in a timely, fair,
FIFO-by-`occurred_at` order, and RLS would either block it entirely
(fail-closed, per ADR 0004's own design) or require granting the
runtime role a `BYPASSRLS`-equivalent, which ADR 0021 explicitly rules
out for the ordinary runtime role. Every row still carries `school_id`
explicitly (nullable, for School-scoped events; null for a genuinely
platform-wide event) so every downstream consumer — including
`WebhookFanoutConsumer`, which DOES need to scope its own tenant-owned
lookups by that `school_id` — remains fully tenant-aware even though
the outbox table itself is not RLS-scoped. `ProcessOutboxEventJob`
establishes real `TenantContext` (via `TenantContext::set($school)`)
before running any consumer, so every consumer's OWN tenant-owned
reads/writes (e.g. `WebhookFanoutConsumer`'s `webhook_subscriptions`
query) are still RLS-protected at that layer — the outbox table's
central nature does not weaken isolation anywhere data is actually
tenant-owned.

## Retry expectations

`ProcessOutboxEventJob` has `$tries = 5`, backoff `[5, 15, 30, 60]`
seconds. A transient failure (a consumer's dependency being briefly
unavailable) retries automatically; a failure in one consumer does not
prevent successful consumers from having already receipted their own
work (see above), so a retry only re-attempts whichever consumer(s)
actually failed. There is no dead-letter table yet for an event that
exhausts all retries — `domain_event_outbox.status` stays `dispatched`
(it was successfully handed to the queue) and Laravel's own
`failed_jobs` table captures the exhausted job; a dedicated outbox-level
dead-letter/alerting path is deferred to the Phase 0C.4 observability
checkpoint, not invented here.

## Rationale

- Writing the outbox row in the SAME transaction as the business state
  change is the entire mechanism that makes the pattern transactional
  — there is no other way to guarantee "the event exists if and only if
  the state change committed" using only PostgreSQL and Laravel's
  existing tooling, and this checkpoint deliberately does not reach for
  a heavier two-phase-commit or change-data-capture mechanism to get
  the same guarantee more expensively.
- `FOR UPDATE SKIP LOCKED` for the dispatcher (rather than, say, an
  application-level advisory lock or a single-dispatcher-instance
  assumption) means horizontal scaling of the dispatcher is safe by
  construction from day one, without a "don't run two of these" runbook
  note that inevitably gets violated during an incident.
- Database-unique-constraint-backed consumer receipts (not a
  Redis-only or in-memory dedup) are the same authoritative-database-
  constraint principle already applied everywhere else in this
  codebase (API idempotency, ADR 0026's webhook attempt numbering) —
  consistency of mechanism matters as much as correctness of any one
  instance of it.

## Alternatives considered

1. **Kafka, RabbitMQ, AWS EventBridge, or another dedicated event-
   streaming platform.** Rejected for the same reason ADR 0001 rejected
   microservices generally: no current requirement (event volume,
   fan-out breadth, cross-service consumption) justifies the
   operational cost of running and operating a distributed broker
   alongside PostgreSQL/Redis, and Laravel's queue + a Postgres outbox
   table already provides the durability guarantee that matters most
   (never silently drop an event). Revisit only if a genuine
   requirement emerges — a second independently-deployed service
   needing to consume School OS's domain events over the network
   without going through an HTTP tool contract (ADR 0013/0014) or a
   webhook subscription (ADR 0018/0026) — not preemptively.
2. **Change Data Capture (CDC) off the business tables directly**
   (e.g. Debezium reading the Postgres WAL). Rejected: adds a
   significant new infrastructure dependency and blurs the line
   between "what changed in a table" and "what business fact occurred"
   — a single business action can touch multiple tables while
   representing one logical event, which an application-level outbox
   insert captures naturally and CDC would require reconstructing.
3. **No outbox at all — dispatch queued listeners directly from
   `event()` and accept the crash-window risk.** Rejected outright:
   this is exactly the failure mode (ADR Context above) the pattern
   exists to close, and accepting it "for now" in a school ERP handling
   financial and student-status transitions was judged an unacceptable
   default for the first module that uses events, not a reasonable
   temporary shortcut.

## Consequences

- Every future domain event MUST implement `ShouldBeOutboxed` and go
  through this path — there is no sanctioned way to fire a
  business-significant event that skips the outbox, by construction
  (Laravel's interface-listener discovery means implementing the
  interface is both necessary and sufficient).
- `domain_event_outbox`/`event_consumer_receipts` being central,
  non-RLS tables is a permanent, reviewed exception to the "every
  table is RLS-protected" default — any future engineer proposing
  another central/non-RLS table must point to an equally explicit,
  reviewed justification, not assume this one sets a precedent for
  convenience.
- The outbox table's retention/pruning strategy is not yet decided
  (mirrors the same open question already documented for
  `webhook_deliveries`/`webhook_delivery_attempts` in
  `docs/architecture/INTEGRATIONS.md`) — deferred, not forgotten.
  *Phase 0C closeout (2026-09-23):* webhook delivery-history pruning now
  exists (`platform:webhook-deliveries-prune`); outbox retention remains
  deliberately deferred, because deliveries read the original event
  payload from this table — see `docs/architecture/PHASE-0C-CLOSEOUT.md`
  section 6.

## Future extraction/evolution path

If a genuine need for a distributed broker emerges later (e.g. a
separately-deployed analytics service needing to consume every domain
event in near-real-time without polling School OS's API), the
extraction path is: `DispatchOutboxEvents` becomes a WAL/outbox-
publisher pushing to the broker instead of (or in addition to) Laravel's
queue, `domain_event_outbox` remains the durable source of truth and
transactional boundary (its role does not change), and every existing
consumer continues working unmodified since `EventConsumer` is an
application-level abstraction already decoupled from "how the event
physically arrived." No current module needs to be redesigned in
anticipation of this — the outbox table itself is already the seam a
future broker would attach to.

## Note on this ADR's timing

This ADR is dated at the time of writing (Phase 0C.3A), documenting
architecture that was implemented and proven (Proof A, `EndToEndProofATest`)
earlier in Phase 0C. The codebase referenced
`docs/architecture/adr/0025-transactional-outbox.md` from multiple
migration docblocks and other documents throughout Phase 0C and 0C.3
before this file existed — a documentation gap this checkpoint closes
by writing down what was already decided and built, not by making a
new decision retroactively.
