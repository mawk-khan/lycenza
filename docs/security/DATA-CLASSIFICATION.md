# School OS — Data Classification

> **This document establishes an architectural classification model to
> drive engineering controls (access, storage, logging, AI exposure). It
> is written by engineering, not legal counsel, and makes no claim about
> compliance with any specific law or regulation.** Anywhere this
> document says a legal/compliance decision is required, that means
> exactly that — the product must not represent itself as compliant with
> India's Digital Personal Data Protection Act (DPDP Act, 2023), any
> education-sector-specific regulation, or any other law until a
> qualified legal review has actually happened. Flagged explicitly below
> as **[LEGAL REVIEW REQUIRED]**.

## Classification tiers

| Tier | Definition | Handling baseline |
|---|---|---|
| **Public** | Safe for anyone to see, including unauthenticated visitors (e.g. a school's public admissions-inquiry page copy). | No special controls. |
| **Internal** | Not secret, but not meant for the public — internal operational data (e.g. a non-sensitive configuration value, a public holiday calendar). | Requires authentication; no special encryption/retention beyond normal system data. |
| **Confidential** | Business-sensitive; disclosure would harm the school or the product, but is not personal data (e.g. internal financial summaries, vendor contract terms). | Requires authentication + capability check; excluded from routine debug logging. |
| **Sensitive** | Personal data of an identifiable individual, not in the highest-risk categories below (e.g. a guardian's phone number, an employee's address). | Requires authentication + capability check, tenant-scoped by construction (`docs/architecture/TENANCY.md`); excluded from logs and error messages by default; access is audited (ADR 0017). |
| **Highly Sensitive** | Data whose exposure carries the highest harm potential: **children's personal data**, health records, government identifiers, authentication secrets, and financial account details. | Everything in Sensitive, plus: minimized default visibility (fetched only when a specific capability needs it, not included in broad list/summary views by default), and — for the categories below — explicit additional controls. |

## Data categories mapped to tiers

| Category | Tier | Notes |
|---|---|---|
| **Student data (general)** — name, class/section, enrollment status | Sensitive | Elevated to Highly Sensitive in combination with health, government-ID, or biometric data. |
| **Children's data specifically** | Highly Sensitive | Students are, for most of this product's user base, minors. India's DPDP Act, 2023 imposes specific obligations around processing children's data (including consent-related requirements). **Architecture/backend implementation for the StudentMark checkpoint specifically is approved with conditions** by Lead Privacy Counsel & Data Protection Officer — India Operations, 2026-09-03 (`docs/security/STUDENTMARK-CHILDRENS-DATA-DETERMINATION.md`) — one condition being the processing-authorization registry below (ADR 0038). This approval does **not** extend to production enablement, Student-facing marks, Guardian-facing marks, result publication, report cards, or transcripts — each of those remains **[LEGAL REVIEW REQUIRED]**/separately withheld pending its own determination, and any OTHER future module processing Student data outside StudentMark's approved scope must still be reviewed by qualified counsel before it ships to real schools. |
| **Guardian data** | Sensitive | Contact details, relationship to student. |
| **Visitor data** (name, optional phone, visit purpose, Campus, host Employee, check-in/check-out timestamps, optional gate-pass identifier) | Sensitive | Ordinary personal data of a non-Student/non-Employee individual, the same tier as Guardian contact data — **conditional on excluding** government-ID numbers/scans, biometrics/facial recognition, and retained photographs, each of which would independently elevate this to Highly Sensitive (government identifiers and biometrics also separately trigger the `[LEGAL REVIEW REQUIRED]` gates below). Visit `purpose` is free text and must never be treated as a Safety/incident record — see `docs/modules/VISITOR.md` §18/§24; a Safety/incident-management module, if built, is a separate future classification decision, not covered by this row. |
| **Hostel residency data** (Hostel/Room/Bed structural identifiers, a Student's Bed assignment and its start/end dates) | Sensitive | Ordinary personal data linking a Student to a physical residence within a School, the same tier as ordinary Student personal data — **conditional on excluding** health/medical data, government-ID numbers, and biometric data, each of which would independently elevate this to Highly Sensitive (government identifiers and biometrics also separately trigger the `[LEGAL REVIEW REQUIRED]` gates below). No Fees/billing/payment-status data is collected by this module — see `docs/modules/HOSTEL.md` §16/§21; a future Fees/Finance integration would introduce its own Highly Sensitive financial data, not covered by this row. |
| **Inventory data** (Item catalogue, stock levels, Location directory, operational StockMovement history) | Confidential | Business/operational data, not personal data — every read requires a specific capability (`inventory.directory.view`/`inventory.stock.view`), not merely an authenticated session, which is what distinguishes this from the `Internal` tier above. **Conditional on excluding** costing/valuation/Finance data and Employee/Student custody, neither of which this module collects — see `docs/modules/INVENTORY.md` §4/§12/§14; a future costing or custody extension would introduce its own Highly-Sensitive/Sensitive data respectively, not covered by this row. |
| **Canteen catalogue/recipe/outlet data** (Outlet directory, menu Item catalogue, recipe requirements) | Confidential | Business/operational data, not personal data — every read requires a specific capability (`canteen.directory.view`), not merely an authenticated session, matching the same `Confidential`-vs-`Internal` distinction the Inventory row above draws (this tier's own worked example: "internal financial summaries, vendor contract terms" — operational data). No Student/Guardian personal data appears in this row — see `docs/modules/CANTEEN.md` §4. |
| **Canteen Order / Order line data** (which Student ordered what, when, for how much) | Highly Sensitive | Links an identifiable Student — Highly Sensitive per the "Children's data specifically" row below, Students are minors — to a financial transaction — Highly Sensitive per the "Financial data" row below. The combination of a child's identity and a monetary amount is exactly this tier's own "highest harm potential" criterion, not merely ordinary Student personal data (the "Student data (general)" row above). This is why the Order list/summary endpoint deliberately excludes every money field and the line array — this tier's "minimized default visibility" handling baseline applied literally. See `docs/modules/CANTEEN.md` §4/§14. |
| **CanteenBillingConfiguration** (which two LedgerAccounts Canteen order fulfillment posts a Charge against) | Highly Sensitive | The same tier as the "Financial data" row below (financial account/configuration data), not merely `Confidential` like the catalogue row above — gated by its own `canteen.settings.view`/`.manage` capability pair, deliberately narrower than `canteen.directory.*`/`canteen.orders.*`. See `docs/modules/CANTEEN.md` §4/§9/§15. |
| **Employee (HR) data** | Sensitive | Elevated to Highly Sensitive for government identifiers, bank details, and any health data collected. |
| **Timetable data** (`TimetablePeriod` catalogue, `TimetableEntry` weekly schedule rows) | Sensitive | A `TimetableEntry` identifies a specific Employee (the teacher) and states their recurring weekly location and time (Room + Period + day-of-week) — ordinary personal data of an identifiable individual, directly analogous to this tier's own "an employee's address" example, not merely `Confidential` like a purely operational catalogue (it names a specific person). Not Highly Sensitive — no health, government-ID, biometric, or financial-account data is involved anywhere in this module, and every teacher presenter is minimized to `id`/`fullName` only (never `work_email`/`work_phone`). No Student relationship exists in this module at all. See `docs/modules/TIMETABLE.md` §5/§6. |
| **Student attendance data** (`AttendanceSession` register headers, `AttendanceRecord` per-Student statuses) | Sensitive | An AttendanceRecord states whether an identifiable minor was present, absent, late or excused for a specific class on a specific date — ordinary personal data of an identifiable individual, and of a child, but deliberately NOT Highly Sensitive because the module stores no health data, no medical or other absence reason, no government identifier, no biometric data, no financial amount and no Guardian PII. That boundary is structural, not merely conventional: the `attendance_records` table has no reason/note/remark/minutes-late/evidence column of any kind and no `student_id` column (Student identity is derived through `StudentEnrollment`), and `Tests\Feature\Attendance\AttendanceArchitectureGuardTest` fails if one is ever added. `excused` records the generic status ONLY and never why — recording a medical explanation would move this row into the Health tier below and requires that tier's own **[LEGAL REVIEW REQUIRED]** gate first. Every Student projection is minimized to id + roll number + composed display name; every teacher projection to `id`/`fullName` (never `work_email`/`work_phone`), matching the Timetable row above. Gated by `attendance.view`/`attendance.manage`; admin-only in v1 (no Student, Guardian or teacher self-service surface exists). See `docs/modules/ATTENDANCE.md` §4/§13. |
| **Syllabus/curriculum content** (`SyllabusUnit` — the ordered units of instructional content a SubjectOffering is expected to cover) | Confidential | Business/academic operational data, NOT personal data — a SyllabusUnit stores no Student, Guardian, Employee or teacher identity of any kind (no `student_id`, `student_enrollment_id`, `teacher_id` or `user_id` column exists, and `Tests\Feature\Syllabus\SyllabusOpenApiCoverageTest` pins the exposed property set to exactly id/subjectOfferingId/code/title/sequence/status). Every read requires a specific capability (`syllabus.view`), not merely an authenticated session, matching the Canteen catalogue row above. Deliberately NOT Sensitive: the Timetable row below is Sensitive only because a `TimetableEntry` identifies a specific Employee and states their recurring location and time — a SyllabusUnit names no one. It carries no `description`, free-text note, learning outcome or attachment, so no Student-specific, medical, safeguarding or behavioural commentary can be recorded against it. Attaching a named teacher in a future Curriculum Delivery or Lesson Planning checkpoint would elevate THAT entity to Sensitive by the Timetable row's exact reasoning; this row does not cover it. See `docs/modules/ACADEMICS.md` §8. |
| **Curriculum delivery records** (`CurriculumDelivery` — which `Section` has covered which `SyllabusUnit`, and when) | Confidential | Business/academic operational data, NOT personal data — a CurriculumDelivery stores no Student, Guardian, Employee or teacher identity of any kind. No `teacher_id`, `employee_id`, `user_id`, `student_id` or enrollment-id column exists, and `Tests\Feature\CurriculumDelivery\CurriculumDeliveryArchitectureGuardTest` asserts the closed column set so one can never be added silently; `Tests\Feature\CurriculumDelivery\CurriculumDeliveryOpenApiCoverageTest` pins the exposed property set to exactly id/sectionId/subjectOfferingId/syllabusUnitId/startedOn/completedOn/status. A **Section is an organisational cohort, not an individual** — naming one identifies no person, which is what separates this row from the Timetable row below (Sensitive only because a `TimetableEntry` identifies a specific Employee). It carries no description, note, objective, lesson content or attachment of any kind, so no Student-specific, behavioural or instructional commentary can be recorded against it, and it holds no mark, grade or assessment (those are Examinations' scope). **Excluding teacher identity is what deliberately keeps this record non-personal**: attaching a named teacher in a future checkpoint would elevate THIS entity to Sensitive by the Timetable row's exact reasoning, and would require the same re-tier in the same branch. Every read requires a specific capability (`curriculum.delivery.view`), not merely an authenticated session; admin-only in v1 (no Student, Guardian or teacher self-service surface exists). See `docs/modules/ACADEMICS.md` §18.9. |
| **Examination definitions** (`Examination` — the named assessment windows a School holds in an AcademicYear) | Confidential | Business/academic operational data, NOT personal data — an Examination stores no Student, Guardian, Employee, teacher or invigilator identity of any kind. No `student_id`, enrollment id, `teacher_id`, `employee_id`, `user_id` or `invigilator_id` column exists, and `Tests\Feature\Examinations\ExaminationArchitectureGuardTest` asserts the closed column set so one can never be added silently; `Tests\Feature\Examinations\ExaminationOpenApiCoverageTest` pins the exposed property set to exactly id/academicYearId/code/name/startsOn/endsOn/status. It states only that a School scheduled a named window within a year — it is a WINDOW, not a paper, and holds no mark, grade, score, result, publication state, report card or transcript (those are later Examinations checkpoints). It carries no description, instructions, note or attachment of any kind, so no Student-specific or behavioural commentary can be recorded against it. Every read requires a specific capability (`examinations.definitions.view`), not merely an authenticated session, matching the Syllabus and Curriculum delivery rows above; admin-only in v1 (no Student, Guardian or teacher self-service surface exists). **Three future additions would each elevate THAT entity to Sensitive**, requiring the re-tier in the same branch: attaching an invigilator/teacher identity (by the Timetable row's exact reasoning), recording Student marks, or recording individual results — the last two being per-Student academic records by the Student attendance row's reasoning, and additionally engaging the children's-data **[LEGAL REVIEW REQUIRED]** gate above for any Student- or Guardian-facing surface. See `docs/modules/EXAMINATIONS.md` §9. |
| **Examination papers** (`ExaminationPaper` — one SubjectOffering assessed within one Examination, its scheduled sitting and maximum marks) | Confidential | Business/academic operational data, NOT personal data — an ExaminationPaper stores no Student, Guardian, Employee, teacher or invigilator identity of any kind. No `student_id`, enrollment id, `teacher_id`, `employee_id`, `room_id` or `invigilator_id` column exists, and `Tests\Feature\Examinations\ExaminationPaperArchitectureGuardTest` asserts the closed column set so one can never be added silently; `Tests\Feature\Examinations\ExaminationPaperOpenApiCoverageTest` pins the exposed property set to exactly id/examinationId/subjectOfferingId/scheduledOn/startsAt/endsAt/maxMarks/status. `schoolId` and every internal integrity pin (`academicYearId`, `campusId`, `gradeLevelId`) are server-derived and never exposed. It states only that a SubjectOffering is assessed within an Examination, when, and out of how many marks — it holds no score, grade, result, publication state, report card or transcript (those are later Examinations checkpoints). It carries no description, instructions, note or attachment of any kind. Every read requires a specific capability (`examinations.papers.view`), a sibling of `examinations.definitions.view`, not merely an authenticated session; admin-only in v1. **The same three future additions as the Examination row above would each elevate THIS entity to Sensitive**, requiring the re-tier in the same branch: attaching an invigilator/teacher identity, recording a Student roster snapshot, or recording Student marks (`StudentMark`) — the last two additionally engaging the children's-data **[LEGAL REVIEW REQUIRED]** gate above. See `docs/modules/EXAMINATIONS.md` §18.10. |
| **Grade scales and bands** (`GradeScale`/`GradeBand` — a School-owned percentage-to-grade mapping) | Confidential | Business/academic reference data, NOT personal data — GradeScale and GradeBand store no Student, Guardian, Employee, teacher or invigilator identity of any kind, and no Examination/ExaminationPaper/AcademicYear/GradeLevel/Subject reference either (wholly independent of the Examination chain — see ADR 0035). No `student_id`, enrollment id, `teacher_id`, `employee_id`, `examination_id` or `grade_level_id` column exists on either table, and `Tests\Feature\Examinations\GradeScaleArchitectureGuardTest` asserts the closed column set on both so one can never be added silently; `Tests\Feature\Examinations\GradeScaleOpenApiCoverageTest` pins the exposed property sets to exactly id/code/name/status/bands (GradeScale) and id/minPercentage/label (GradeBand). `schoolId` is server-derived and never exposed. It states only a School's own grading policy — a percentage threshold mapped to a label — and holds no per-Student mark, score or result of any kind (those remain later, gated Examinations checkpoints). GradeBand `label` and GradeScale `name` values are additionally never included by value in audit metadata, only by field name, since they are School-authored free text. Every read requires a specific capability (`examinations.grade_scales.view`), a sibling of `examinations.definitions.view`/`examinations.papers.view`, not merely an authenticated session; admin-only in v1. **Attaching this classification's mapping to an actual Student mark** (the future `StudentMark` checkpoint) engages the children's-data **[LEGAL REVIEW REQUIRED]** gate above for THAT entity — GradeScale/GradeBand themselves do not, and ship fully independently of that blocker. See `docs/modules/EXAMINATIONS.md` §19. |
| **LMS Learning Content / Assignment** (`LearningContent` — a School-authored instructional resource; `Assignment` — title, instructions, resource attachments, due date, lifecycle) | Confidential | Business/academic operational data, NOT personal data — both are staff-authored and store no Student, Guardian, teacher or invigilator identity of any kind, the same reasoning as `SyllabusUnit`/`Examination`/`ExaminationPaper`. Every read requires a specific capability (`lms.content.view`/`lms.assignments.view`), not merely an authenticated session; capability-only, admin/principal-granted in v1 (no teacher-ownership model exists yet — see ADR 0039 §6/`docs/modules/LMS.md` §7). **Attaching a Student roster/submission relationship does not itself elevate this row** — that relationship lives on the separate Submission row below, mirroring how `ExaminationPaper` stays Confidential despite pinning a `SubjectOffering` with a real roster. See ADR 0039 and `docs/modules/LMS.md` §5. |
| **LMS Submission / Student Work Product** (`Submission` — was proposed to hold Student-authored coursework text and/or files, submission/revision timestamps, the Assignment↔Student relationship, non-authoritative teacher feedback) | **OUT OF SCOPE — LMS SUBMISSION FEATURE CANCELLED 2026-09-05** | **This row is historical.** Submission was never implemented, was classified Sensitive with a `[LEGAL REVIEW REQUIRED]` gate (Phase 0I.4, `docs/security/LMS-SUBMISSION-LEGAL-REVIEW.md`), and that escalation received no qualifying legal response before the product owner cancelled the underlying capability entirely as a product-scope decision — see `docs/architecture/adr/0039-lms-domain-contract.md`'s Submission cancellation addendum. **This is not a legal clearance and must never be read as one**: the classification/gate is retired because the feature no longer exists, not because a qualified legal answer was obtained. The original reasoning is preserved for provenance in case this scope is ever reopened: Submission would have been the first checkpoint in this roadmap to durably store unbounded, Student-authored free-text and/or file content, rather than structured facts about a Student — every prior Sensitive-tier Student/academic module (`AttendanceRecord`, `SyllabusUnit`, `CurriculumDelivery`, `Examination`, `ExaminationPaper`) deliberately excludes free text for exactly this reason. That gate was distinct from the `StudentMark` flag above and was never waived merely because Documents storage (ADR 0012) already exists. **If this scope is ever reopened**, the legal-review question must be re-raised from first principles, not assumed resolved by the passage of time or by this cancellation. See ADR 0039 §4/§5 (including its 2026-09-05 cancellation addendum) and `docs/modules/LMS.md` §0/§5/§6. |
| **Financial data** (fees, invoices, payroll, payment instrument references) | Highly Sensitive | Never store raw payment-card data in School OS's own database — see the financial-correctness rules in `docs/architecture/ARCHITECTURE.md` §10 and PCI-DSS scope considerations, which are **[LEGAL/COMPLIANCE REVIEW REQUIRED]** once a real payment gateway integration (ADR 0018) is designed. |
| **Health data** | Highly Sensitive | Medical conditions, allergies, incident records. **[LEGAL REVIEW REQUIRED]**: may separately qualify as a sensitive personal data category under applicable law; a dedicated review is required before the Health module (`docs/architecture/DOMAIN-MAP.md`) is implemented. |
| **Government/statutory identifiers** (e.g. Aadhaar-linked references, PAN, other ID numbers collected for admissions/HR/compliance) | Highly Sensitive | **[LEGAL REVIEW REQUIRED]**: collection, storage, and masking requirements for government identifiers are subject to specific Indian regulatory requirements (including sector-specific Aadhaar-handling rules) that must be reviewed before any module collects them — do not assume storing a raw identifier is acceptable without that review. |
| **Documents/files** (birth certificates, photos, transfer certificates, medical records, HR documents) | Classification inherited from what the document contains | A birth certificate scan is Highly Sensitive; a public event photo may be Public — the Documents module (ADR 0012) must tag each stored document with its actual classification, not a blanket default. |
| **Authentication secrets** (passwords/hashes, API keys/tokens, the Laravel↔AI Gateway service token, and — Phase 0H.4D-P1, ADR 0037 — a User's TOTP secret and MFA recovery codes) | Highly Sensitive | Never logged, never included in error messages, never returned by any API response (see ADR 0016; `services/ai/app/core/config.py`'s `redact` conventions for the devtools/audit layers that must respect this). The TOTP secret uses the same reversible `encrypted` cast as `webhook_endpoints.secret_encrypted`; recovery codes use the same one-way `hashed` cast as the password itself — see ADR 0037. |
| **Student processing-authorization records** (`StudentProcessingAuthorization` — Phase 0H.4D-P2, ADR 0038: which basis, Guardian-relationship/Student provider reference, recording staff User, timestamp) | Highly Sensitive | More sensitive than the "Student data (general)" row above: this record IS the legal-basis assertion permitting School processing of a (commonly minor) Student's protected data, not merely a derived eligibility fact. Never exposes DOB, Guardian/Student names, or free-text `note` content in audit metadata — only ids, purpose, basis_type, and status. Gated by `students.processing_authorizations.view`/`.manage` (School-scoped, `school_admin`/`principal` only) composed with `mfa` (ADR 0037) — the first genuine production route requiring both. See ADR 0038. |
| **Production infrastructure and recovery material** (ADR 0050, contract — Phase 0O.4; tooling Phase 0O.4A): secret values; secret references; infrastructure configuration (topology, network ranges, trusted proxies); Terraform state; database and object-storage backups; backup manifests; restore-drill evidence | Secret values, Terraform state and backups: **Highly Sensitive**; secret references, infrastructure configuration, backup manifests and drill evidence (no payloads): **Confidential** | Backups contain everything the live system holds, including children's data; backup sets are not readable or deletable with application credentials. Operational backup windows (35 days for PostgreSQL) are not legal retention periods. Phase 0O.4A operator commands (`platform:verify-database`, `-storage`, `-restore`) print codes, counts and timestamps only — never credentials, endpoints, error text, filenames, keys or payloads; drill records (`docs/operations/RESTORE-DRILL-RECORD.md`) follow the same rule. |
| **Operational telemetry** (ADR 0051, Phase 0O.5): application logs (Laravel, AI Gateway, nginx), operational metrics, alert history | **Confidential** (logs and metrics alike; never Public) | Logs may carry pseudonymous identifiers already in the request context (School, actor, elevation, API client ids), request/correlation ids and, for security events, source IP — never Highly Sensitive payload data, credentials, document contents or AI prompts/outputs; a Sensitive identifier a specific security event needs is documented at its call site, not by lowering the tier. Metrics carry no tenant/person/record identifier by construction. Retention: logs 30 days, metrics 90 days — operational only, independent of audit, legal and backup retention. Access: authorized operators only; never School users; no public dashboards. Logs are never audit evidence. | **External API credential records** (ADR 0049; built Phase 0O.3 — `personal_access_tokens`, `api_clients`, `api_client_credentials`, events `auth.api_token.*` and `integrations.api_client.*`): human API-token metadata (owner user, name, scopes, expiry, `last_used_at`); partner API-client metadata (School, name, scopes, status, non-secret `key_id`, expiry, `last_used_at`); token/credential hashes; issuance, rotation, revocation and authentication-denial audit events | Human token metadata: **Sensitive**; partner client metadata: **Confidential**; hashes: **Highly Sensitive**; the audit events: **Highly Sensitive** | Hashing does not lower a credential's tier (the "Authentication secrets" row). | **Bootstrap School Admin relationship** (ADR 0047: which user is, or was, a School's bootstrap administrator — their ordinary membership and `school_admin` assignment, and replacement history) | **Sensitive** (owner-approved v1, 2026-09-25) | Links an identifiable person to administrative authority in a School (the same tier as human Group administrative grants). Shown on the platform lifecycle page only while the School is `provisioning`; afterwards it is an ordinary School membership. Classification of ordinary memberships in general is still open. |
| **School lifecycle and bootstrap audit evidence** (ADR 0047: `platform.school.created`, `.bootstrap_admin_assigned`, `.bootstrap_admin_replaced`, `.activated`, `.suspended`, `.resumed`, `.lifecycle_denied`) | **Highly Sensitive** (the existing ADR 0046 platform audit treatment) | Platform ledger only, never duplicated to the School ledger; identifiers and codes only (user/membership ids, from/to status, suspension reason code, denial outcome code) — never names, slugs, emails or free text. Reviewed through the platform audit log envelope (metadata hidden). |
| **Automation records** (rule instances, executions, execution attempts, review items — ADR 0043; built in Phase 0L.6 for the academic year set-up review rule, which references an Academic Year by id only) | **Inherits the strictest tier of the source entities and action concerned** | Records hold identifiers, codes, statuses and timestamps only — never a source payload, snapshot, name, contact detail, amount or free text, and failure details are stable codes, not exception messages. A review item referencing a Guardian, Student or Employee record is at least Sensitive; opening the referenced record still requires the source module's own capability. Retention is part of the repository-wide **[LEGAL REVIEW REQUIRED]** retention gate. |
| **AI prompts/context** | Classification inherited from the data included in the prompt/context | A prompt built from Sensitive or Highly Sensitive ERP data (e.g. a fee-reminder draft referencing a guardian's contact details) is itself Sensitive/Highly Sensitive for logging, audit-storage, and provider-selection purposes — see `docs/ai/AI-SECURITY.md`'s data-exposure controls. This has a direct consequence for provider selection: a provider whose data-handling/retention terms are inadequate for a given classification tier must not be used for prompts at that tier — a **[LEGAL/COMPLIANCE REVIEW REQUIRED]** gate before any real provider integration (ADR 0013) goes live with real school data. The same inheritance applies to tool arguments, tool results, model outputs (a drafted message can itself contain Highly Sensitive data) and AI audit metadata; transforming data into prose never lowers its tier. What the provider review must answer, and the recorded approval it requires, is `docs/security/AI-PROVIDER-LEGAL-COMPLIANCE-GATE.md` (status: BLOCKED). |
| **Aggregated / derived / statistical data (Analytics)** — counts, totals, averages, percentages, trends, grouped statistics, dashboard summaries, and report outputs computed FROM other categories in this table (ADR 0040, Phase 0L.1) | **Inherits the strongest tier among its source data by default** | Not a new tier — a rule for how existing tiers apply to DERIVED values, not just raw records. A count touching Highly Sensitive source data (e.g. financial, health, or a children's-data combination) defaults Highly Sensitive, the same combinatorial-elevation reasoning the "Canteen Order / Order line data" row above already establishes for a single record ("the combination of a child's identity and a monetary amount is exactly this tier's own 'highest harm potential' criterion") — applied here to an aggregate instead of a row. **A downgrade requires ALL of**: the cohort/cell meets the minimum-cohort-size threshold (below); no combination of the aggregate's own grouping dimensions can re-derive an individual's identity or category membership (a cell of size 1 within a large School-wide total is still unsafe); the aggregate does not itself disclose Highly-Sensitive category membership (e.g. "3 students have a recorded health condition" stays Highly-Sensitive-shaped as a count, independent of cohort size). **[LEGAL/PRODUCT/SECURITY REVIEW REQUIRED]: the minimum-cohort-size / small-cohort-suppression threshold is not yet set.** The architectural RULE is frozen (a cell below the threshold must be omitted, bucketed into a wider group, or the grouping declined — never rendered as an exact small number) but the exact number is an open gate, deliberately not invented here — the same discipline already applied to retention periods ("Engineering controls this classification drives" below) and to LMS Submission's classification review. Worked examples this rule must cover: attendance rate for a very small class; count of Students with outstanding fees; disciplinary counts for a tiny group; payroll statistics for a small department; examination results for a small cohort. **No Analytics read model capable of producing a small-cohort cell may ship until this threshold is set.** Aggregation must never be treated as an implicit privacy bypass merely because "it's just a count, not the individual record." **Scope of the threshold (ADR 0040 2026-09-23 amendment):** it applies wherever a cell value or its denominator counts people or could disclose information about people; pure non-person object/process aggregates (e.g. syllabus-unit coverage, Phase 0L.2-1) are outside the cohort-size threshold but keep their inherited tier and all normal authorization, tenancy and audit controls. Person-counting Analytics fails closed while the threshold is unset. See ADR 0040 §6 and `docs/modules/ANALYTICS.md` §6/§13. |

## Engineering controls this classification drives

- **Access control:** every Sensitive/Highly Sensitive field requires a
  capability check (`docs/security/AUTHORIZATION.md`), not just
  authentication.
- **Logging:** Sensitive and Highly Sensitive values must never appear
  in application logs, error messages, or exception traces — this is a
  code-review checklist item (root `CLAUDE.md`), not just a policy
  statement.
- **AI exposure:** a tool exposed to an AI agent (ADR 0014) must be
  designed to return only what that agent's purpose requires, informed
  by classification — a fee-collection agent's tools should not surface
  Health-tier data even if it's in an adjacent table.
- **Audit:** access to Sensitive/Highly Sensitive data is itself
  auditable (ADR 0017) — not just changes to it.
- **Retention:** retention periods per category are a
  **[LEGAL REVIEW REQUIRED]** decision, not yet made — flagged here so
  it is designed deliberately once the first module handling
  Sensitive/Highly Sensitive data is built, rather than defaulting to
  "keep everything forever" by omission.
- **Aggregation/derivation:** a derived value's classification tracks
  its source data (see the "Aggregated / derived / statistical data"
  row above) — building an Analytics/reporting feature does not create
  a lower-classification escape hatch for data that would otherwise be
  Sensitive/Highly Sensitive in its raw form.

## What this document does not do

It does not implement any technical control itself (no encryption
scheme, no field-level access-control code exists yet in Phase 0A) —
it is the classification reference those future controls, and the
capability design in `docs/security/AUTHORIZATION.md`, must be built
against.
