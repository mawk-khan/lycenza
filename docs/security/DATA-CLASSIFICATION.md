# School OS — Data Classification

> **This document establishes an architectural classification model to
> drive engineering controls (access, storage, logging, AI exposure). It
> is written by engineering, not legal counsel, and makes no claim about
> compliance with any specific law or regulation.** Anywhere this
> document says a legal/compliance decision is required, that means
> exactly that — the product must not represent itself as compliant with
> India's Digital Personal Data Protection Act (DPDP Act, 2023), any
> education-sector-specific regulation, or any other law until a
> qualified legal review has actually happened. Flagged explicitly below
> as **[LEGAL REVIEW REQUIRED]**.

## Classification tiers

| Tier | Definition | Handling baseline |
|---|---|---|
| **Public** | Safe for anyone to see, including unauthenticated visitors (e.g. a school's public admissions-inquiry page copy). | No special controls. |
| **Internal** | Not secret, but not meant for the public — internal operational data (e.g. a non-sensitive configuration value, a public holiday calendar). | Requires authentication; no special encryption/retention beyond normal system data. |
| **Confidential** | Business-sensitive; disclosure would harm the school or the product, but is not personal data (e.g. internal financial summaries, vendor contract terms). | Requires authentication + capability check; excluded from routine debug logging. |
| **Sensitive** | Personal data of an identifiable individual, not in the highest-risk categories below (e.g. a guardian's phone number, an employee's address). | Requires authentication + capability check, tenant-scoped by construction (`docs/architecture/TENANCY.md`); excluded from logs and error messages by default; access is audited (ADR 0017). |
| **Highly Sensitive** | Data whose exposure carries the highest harm potential: **children's personal data**, health records, government identifiers, authentication secrets, and financial account details. | Everything in Sensitive, plus: minimized default visibility (fetched only when a specific capability needs it, not included in broad list/summary views by default), and — for the categories below — explicit additional controls. |

## Data categories mapped to tiers

| Category | Tier | Notes |
|---|---|---|
| **Student data (general)** — name, class/section, enrollment status | Sensitive | Elevated to Highly Sensitive in combination with health, government-ID, or biometric data. |
| **Children's data specifically** | Highly Sensitive | Students are, for most of this product's user base, minors. India's DPDP Act, 2023 imposes specific obligations around processing children's data (including consent-related requirements). **Architecture/backend implementation for the StudentMark checkpoint specifically is approved with conditions** by Lead Privacy Counsel & Data Protection Officer — India Operations, 2026-09-03 (`docs/security/STUDENTMARK-CHILDRENS-DATA-DETERMINATION.md`) — one condition being the processing-authorization registry below (ADR 0038). This approval does **not** extend to production enablement, Student-facing marks, Guardian-facing marks, result publication, report cards, or transcripts — each of those remains **[LEGAL REVIEW REQUIRED]**/separately withheld pending its own determination, and any OTHER future module processing Student data outside StudentMark's approved scope must still be reviewed by qualified counsel before it ships to real schools. |
| **Guardian data** | Sensitive | Contact details, relationship to student. |
| **Visitor data** (name, optional phone, visit purpose, Campus, host Employee, check-in/check-out timestamps, optional gate-pass identifier) | Sensitive | Ordinary personal data of a non-Student/non-Employee individual, the same tier as Guardian contact data — **conditional on excluding** government-ID numbers/scans, biometrics/facial recognition, and retained photographs, each of which would independently elevate this to Highly Sensitive (government identifiers and biometrics also separately trigger the `[LEGAL REVIEW REQUIRED]` gates below). Visit `purpose` is free text and must never be treated as a Safety/incident record — see `docs/modules/VISITOR.md` §18/§24; a Safety/incident-management module, if built, is a separate future classification decision, not covered by this row. |
| **Hostel residency data** (Hostel/Room/Bed structural identifiers, a Student's Bed assignment and its start/end dates) | Sensitive | Ordinary personal data linking a Student to a physical residence within a School, the same tier as ordinary Student personal data — **conditional on excluding** health/medical data, government-ID numbers, and biometric data, each of which would independently elevate this to Highly Sensitive (government identifiers and biometrics also separately trigger the `[LEGAL REVIEW REQUIRED]` gates below). No Fees/billing/payment-status data is collected by this module — see `docs/modules/HOSTEL.md` §16/§21; a future Fees/Finance integration would introduce its own Highly Sensitive financial data, not covered by this row. |
| **Inventory data** (Item catalogue, stock levels, Location directory, operational StockMovement history) | Confidential | Business/operational data, not personal data — every read requires a specific capability (`inventory.directory.view`/`inventory.stock.view`), not merely an authenticated session, which is what distinguishes this from the `Internal` tier above. **Conditional on excluding** costing/valuation/Finance data and Employee/Student custody, neither of which this module collects — see `docs/modules/INVENTORY.md` §4/§12/§14; a future costing or custody extension would introduce its own Highly-Sensitive/Sensitive data respectively, not covered by this row. |
| **Canteen catalogue/recipe/outlet data** (Outlet directory, menu Item catalogue, recipe requirements) | Confidential | Business/operational data, not personal data — every read requires a specific capability (`canteen.directory.view`), not merely an authenticated session, matching the same `Confidential`-vs-`Internal` distinction the Inventory row above draws (this tier's own worked example: "internal financial summaries, vendor contract terms" — operational data). No Student/Guardian personal data appears in this row — see `docs/modules/CANTEEN.md` §4. |
| **Canteen Order / Order line data** (which Student ordered what, when, for how much) | Highly Sensitive | Links an identifiable Student — Highly Sensitive per the "Children's data specifically" row below, Students are minors — to a financial transaction — Highly Sensitive per the "Financial data" row below. The combination of a child's identity and a monetary amount is exactly this tier's own "highest harm potential" criterion, not merely ordinary Student personal data (the "Student data (general)" row above). This is why the Order list/summary endpoint deliberately excludes every money field and the line array — this tier's "minimized default visibility" handling baseline applied literally. See `docs/modules/CANTEEN.md` §4/§14. |
| **CanteenBillingConfiguration** (which two LedgerAccounts Canteen order fulfillment posts a Charge against) | Highly Sensitive | The same tier as the "Financial data" row below (financial account/configuration data), not merely `Confidential` like the catalogue row above — gated by its own `canteen.settings.view`/`.manage` capability pair, deliberately narrower than `canteen.directory.*`/`canteen.orders.*`. See `docs/modules/CANTEEN.md` §4/§9/§15. |
| **Fee setup configuration** (FEE.1, ADR 0062: fee heads and their receivable/revenue ledger-account mapping, fee structures, lines, instalment schedules; ledger accounts created through the K1 administration path) | Confidential | School pricing and chart-of-accounts configuration, not personal data -- the Inventory/Canteen catalogue precedent. Every read requires `finance.fee_structures.view` (ledger accounts: `finance.ledger.view`), every write `finance.fee_structures.manage` (`finance.accounts.manage`). Audit metadata carries ids and codes only, never amounts. No tax/GST attribute exists ([LEGAL REVIEW REQUIRED], ADR 0062 §17.5). See `docs/modules/FINANCE.md` "FEE.1 as-built". |
| **Optional-fee selections** (FEE.1, ADR 0062 §8: which Student chose which optional fee for which academic year) | Highly Sensitive | Links an identifiable minor to a financial obligation -- the same combination as the "Canteen Order" row above. Listing requires `finance.fee_structures.view` plus a Student or line filter (never a School-wide dump) and writes a `fee_optional_selection.list_viewed` read audit; audit metadata carries ids only. Selections are withdrawn, never deleted. Retention is the pending E21 decision. |
| **Fee assessment runs, run items and fee assessments** (FEE.2, ADR 0062: which Student was, or will be, charged which fee head for which billing period, and why an item was excluded or failed) | Highly Sensitive | Links identifiable minors to financial obligations -- the "Canteen Order" combination. Read under `finance.charges.view` (items paginated, never a School-wide export); run actions under `finance.fee_assessments.run`; voids under `finance.charges.manage`. Item reasons come from closed catalogues (no free text); a void reason is short staff text and never logged. Audit metadata and the `fee_assessment_run.completed.v1` payload carry ids and counts only, never amounts or names. Retention is the pending E21 decision. |
| **Fee concessions, scholarships, waivers and fee adjustments** (FEE.3, ADR 0062 §14, §21: which Student received which reduction, of which category, for which charge or period, and who requested and approved it) | Highly Sensitive | Links an identifiable minor to a financial obligation **and** can reveal a family's circumstances. Every read requires `finance.fee_concessions.view` and is read-audited once per call (`fee_concession.list_viewed`, `fee_concession.viewed`, `fee_adjustment.list_viewed`); the assessment-run page shows concession projections only to holders of that capability. Categories come from a closed catalogue (`concession`, `scholarship`, `waiver`) and there is deliberately **no free-text note** (owner decision M) -- sibling, staff-ward and RTE labels stay out pending the owner and the ADR 0062 §27 legal answer. Audit metadata and the `fee_concession.*.v1`/`fee_adjustment.*.v1` payloads carry ids and closed codes only, never amounts or names. An adjustment-cancellation reason is short staff text passed only to the Finance reversal and never logged. Concessions and adjustments are never deleted. Retention is the pending E21 decision. |
| **Payment receipts and Student fee statements** (FEE.4, ADR 0062 §17, §18, §21: which Student paid what, when, by which method, against which fees, with receipt numbers; per-charge outstanding balances) | Highly Sensitive | Student-linked financial data (the "Financial data" and "Children's data" rows). A receipt read requires `finance.payments.view` and is audited once (`payment_receipt.viewed`); a statement requires **both** `finance.charges.view` and `finance.payments.view` and is audited once (`fee_statement.viewed`), never on a denial. Nothing is stored beyond the immutable receipt identity (number, series, issue facts) -- amounts and Student facts are read from the Payment, allocations and charges each time; there is no stored balance. The API exposes Student ids, never names; audit metadata and the `payment_receipt.issued.v1` payload carry ids, the series and the issuance mode only -- never amounts, names, receipt numbers or rendered content, and nothing logs a receipt. No tax attribute exists (ADR 0062 J: LEGAL REVIEW REQUIRED — development authorised, production legal sign-off required). No export, PDF or Guardian/Student view. Retention is the pending E21 decision; no purge exists. |
| **Late-fee rules** (FEE.5, ADR 0062 §16.1: scope, grace days, fixed amount or percentage, optional cap, late-fee head) | Confidential | School pricing configuration, no personal data -- the fee-setup row's precedent. Reads require `finance.fee_structures.view`, writes `finance.fee_structures.manage`; audit metadata carries ids and codes only. Legal status of the policy itself: DEVELOPMENT AUTHORISED — PROD LEGAL SIGN-OFF REQUIRED (ADR 0058 E31). |
| **Late-fee runs, run items and late-fee assessments** (FEE.5, ADR 0062 §16.2-§16.3: which Student's charge was, or will be, charged a late fee, with the outstanding balance used and the amount) | Highly Sensitive | Links identifiable minors to financial obligations and reveals payment status (the outstanding). Read under `finance.charges.view` (items paginated, never a School-wide export); run actions under `finance.fee_assessments.run`; voids under `finance.charges.manage`. Items store ids, dates and amounts only -- no Student name, no free text; reasons are closed catalogues. Audit metadata and the `late_fee.assessed.v1` payload carry ids (and currency) only. Never deleted; retention is the pending E21 decision; no purge exists. |
| **Financial periods and close baselines** (E21.3A, ADR 0064: `financial_periods`; per-account cumulative totals `financial_period_account_balances`; per-charge state as of a closed year `financial_period_charge_states` -- amount, allocations, live adjustments, cancellation) | Highly Sensitive (charge states) / Confidential (periods, account totals) | Charge states are per-charge, so Student-linked financial data through the charge, the same as statements. Account totals and periods are School accounting data, not personal data. Reads: periods and blockers under `finance.ledger.view`; baselines have no read surface (verification output names ids and codes only, never amounts). Writes: only the close (`finance.periods.manage` + fresh MFA), append-only, RLS-forced, no runtime DELETE. Periods and account baselines are kept for the School's lifetime. Since E21.3A2 (D8), a charge's carried states expire with its settled unit 8 calendar years after its period closed, and `financial_period_expiries` (append-only lineage: period, time, counts; never amounts or deleted content) records each expired unit. Audit metadata carries the period key, dates, counts and fingerprint, never amounts. |
| **Employee (HR) data** | Sensitive | Elevated to Highly Sensitive for government identifiers, bank details, and any health data collected. |
| **Leave configuration** (HRX.1, ADR 0065: `leave_settings`, `leave_year_start_changes`, `leave_years`, the year-close header `leave_year_closes` (HRX.2), `leave_types`, `leave_policies`, `staff_working_weekdays`, `staff_holidays`, allocation run headers `leave_allocation_runs`) | Confidential | School HR configuration, no per-employee personal data (a run header holds only a year, a type and a count). Reads require `hr.leave.view`; writes require `hr.leave.configure` (runs: `hr.leave.manage`). Forced RLS; retention tenant lifetime (`leave_configuration`). |
| **Leave entitlement and request evidence** (HRX.1–HRX.2, ADR 0065: `leave_policy_assignments` — which policy applies to which EmploymentRecord, when; `leave_ledger_entries` — allocations, adjustments, consumption, reversal, carry/expiry, in integer half-day units; `leave_requests` — dates, day portions, leave type, closed reason code, status; `leave_request_days` — the approval's chargeable-day snapshot; `leave_decisions` — who decided, on which path, closed reason code; `leave_year_close_items` / `leave_year_close_reconciliations` — per-employment closing, carried and lapsed units) | Sensitive | Employee employment evidence (the "Employee (HR) data" row). **No health data:** a leave type named "Sick" is a category label only; no Leave table holds a diagnosis, medical reason, certificate, attachment, free text or biometric (HRX-L1/L2, guarded by `LeaveArchitectureGuardTest`). Reads require `hr.leave.view`; writes `hr.leave.manage`. Forced RLS, append-only ledger. D9 employment evidence (`leave_evidence`, purge participant HRX.6). Never a log field or metric label beyond ids. |
| **Staff attendance evidence** (HRX.3, ADR 0065 §24: `staff_attendance_records` — one EmploymentRecord's presence on one date, each half `present`, `absent` or empty; `staff_attendance_corrections` — append-only before/after of both halves, version step, closed neutral reason code, actor) | Sensitive | An identifiable Employee's presence or absence by date — ordinary personal data. Not Highly Sensitive: no health or absence reason, no medical detail, no free text, no clock time, no device, location, photo or biometric data (structurally absent, `StaffAttendanceArchitectureGuardTest`; HRX-L1/L2 stay open). Leave, holidays and weekly offs are derived, never stored. Reads require `hr.staff_attendance.view` (leave identifiers only with `hr.leave.view` as well); writes `hr.staff_attendance.manage`. Projections are directory-tier. Forced RLS, same-School composite FKs, RESTRICT; D9 retention (`staff_attendance_evidence`, mechanism pending HRX.6). |
| **Timetable data** (`TimetablePeriod` catalogue, `TimetableEntry` weekly schedule rows) | Sensitive | A `TimetableEntry` identifies a specific Employee (the teacher) and states their recurring weekly location and time (Room + Period + day-of-week) — ordinary personal data of an identifiable individual, directly analogous to this tier's own "an employee's address" example, not merely `Confidential` like a purely operational catalogue (it names a specific person). Not Highly Sensitive — no health, government-ID, biometric, or financial-account data is involved anywhere in this module, and every teacher presenter is minimized to `id`/`fullName` only (never `work_email`/`work_phone`). No Student relationship exists in this module at all. See `docs/modules/TIMETABLE.md` §5/§6. |
| **Teaching Assignments** (`TeachingAssignment` — which Employee owns which Section + required SubjectOffering teaching context, for which dates; TCH.2, ADR 0063) | Sensitive | Names an identifiable Employee against a class and a period — ordinary personal data of an identifiable individual, the Timetable row's exact reasoning. Not Highly Sensitive: no health, government-ID, financial or Student data, and no free text (the end reason is a closed catalogue: `completed`, `reassigned`, `employment_ended`). Every projection is directory-tier (Employee id, number and name; never work contact, HR profile or account data; no user ids). Reads require `teaching.assignments.view`, writes `teaching.assignments.manage`; API responses are `Cache-Control: no-store, private`. Audit metadata carries ids, dates and the closed reason only. Rows are ended, never deleted; retention follows the pending ADR 0058 E21 decision. It grants no access by itself: it is one of the required facts for every owned teacher surface (with a verified ActingEmployee and the surface's owned-scope capability) -- Curriculum Delivery (TCH.3), Attendance (TCH.4), Learning Content (TCH.5C) and Assignments (TCH.5D); a teacher sees only their own periods, never other Employees' assignments. See `docs/modules/TEACHING-ASSIGNMENTS.md`. |
| **Student attendance data** (`AttendanceSession` register headers, `AttendanceRecord` per-Student statuses) | Sensitive | An AttendanceRecord states whether an identifiable minor was present, absent, late or excused for a specific class on a specific date — ordinary personal data of an identifiable individual, and of a child, but deliberately NOT Highly Sensitive because the module stores no health data, no medical or other absence reason, no government identifier, no biometric data, no financial amount and no Guardian PII. Gated by `attendance.view`/`attendance.manage` (School-wide, Tier 1). **TCH.4 (ADR 0063 §32)** adds an owned teacher path — `attendance.teacher` AND a verified ActingEmployee AND a TeachingAssignment for the register's class on its date — exposing the same minimized projections for owned classes only. ## Engineering controls this classification drives

- **Access control:** every Sensitive/Highly Sensitive field requires a
  capability check (`docs/security/AUTHORIZATION.md`), not just
  authentication.
- **Logging:** Sensitive and Highly Sensitive values must never appear
  in application logs, error messages, or exception traces — this is a
  code-review checklist item (root `CLAUDE.md`), not just a policy
  statement.
- **AI exposure:** a tool exposed to an AI agent (ADR 0014) must be
  designed to return only what that agent's purpose requires, informed
  by classification — a fee-collection agent's tools should not surface
  Health-tier data even if it's in an adjacent table.
- **Audit:** access to Sensitive/Highly Sensitive data is itself
  auditable (ADR 0017) — not just changes to it.
- **Retention:** retention periods per category are a
  **[LEGAL REVIEW REQUIRED]** decision, not yet made — flagged here so
  it is designed deliberately once the first module handling
  Sensitive/Highly Sensitive data is built, rather than defaulting to
  "keep everything forever" by omission.
  *Cross-reference (2026-09-28):* ADR 0058 §4.12 makes the retention
  decisions for the categories used in v1 a **mandatory Phase 0O closeout
  item** (evidence row E21). This document still records no period.
  *E21.1 (2026-10-01):* the per-category inventory, the open decisions
  (E21-D0–D13) and the determination template are in
  `docs/security/E21-RETENTION-DECISION-REQUEST.md`. A tier never implies
  a period.
  *E21.2 (2026-10-01):* the project-adopted periods (pending final legal
  ratification) are in `docs/security/E21-RETENTION-DETERMINATION.md`.
- **Aggregation/derivation:** a derived value's classification tracks
  its source data (see the "Aggregated / derived / statistical data"
  row above) — building an Analytics/reporting feature does not create
  a lower-classification escape hatch for data that would otherwise be
  Sensitive/Highly Sensitive in its raw form.

## What this document does not do

It does not implement any technical control itself (no encryption
scheme, no field-level access-control code exists yet in Phase 0A) —
it is the classification reference those future controls, and the
capability design in `docs/security/AUTHORIZATION.md`, must be built
against.
