# Phase 0O.6F — Runtime hardening, approved exceptions & artifact requalification (2026-09-26)

**Decision:** `OWNER-0O6E-2026-09-26` ([record](0O.6E-owner-security-decision.md)).
The 12 residual Debian 13 HIGH-without-fix advisories are accepted exactly,

## 1. Runtime hardening (conditions of #1, #3, #4, #7, #8)

| Control | Where | Proof |
|---|---|---|
| never privileged; ALL capabilities dropped, none added; no-new-privileges; the existing non-root user | `infrastructure/release/runtime-security.json` (+ schema `const`s), provider-neutral | `verify-images.sh` starts every application and Gateway container with `--cap-drop ALL --security-opt no-new-privileges:true` and checks `docker inspect` (`false\|["ALL"]\|null\|["no-new-privileges:true"]`) |
| process identity from the kernel | `verify-images.sh` | `/proc/self/status` of each image, then every `/proc/<pid>/status` of the web, three worker and scheduler roles and of the Gateway: Uid ≠ 0, CapPrm/CapEff/CapBnd/CapAmb = 0, NoNewPrivs = 1. The parser rejects root, NoNewPrivs 0, any capability, an empty set, an unhardened container and a `--cap-drop ALL`-only container |
| `mount`/`umount` not setuid | both Dockerfiles: `dpkg-statoverride --update --add root root 0755` | mode 755 plus the dpkg statoverride database entry, in both images |
| setuid/setgid gain nothing | — | under the contract, `chage -l` (setgid `shadow`) cannot read `/etc/shadow` and `mount -t tmpfs` fails. The unhardened **control** shows the same `chage` succeeds, so the test discriminates |
| no user-mountable fstab entry | — | no active `/etc/fstab` line, and none with `user`/`users`/`owner`/`group`/`bind`/`X-mount.*` |
| no weakening in any production definition | `RuntimeSecurityContractTest` (5 tests) | 4 mutations caught: Gateway umount statoverride removed, contract NNP false, an unhardened `in_app`, a `--cap-add SYS_ADMIN` in `processes.json` |

**Root-process audit.** No role runs a root process:
- The entrypoint execs as `www-data`; nginx (master and workers) and the
  PHP-FPM master and pool are all uid 33. Neither `su`/`gosu`/`setpriv` nor
  any privilege switch exists anywhere in `deploy/` or the Dockerfiles.
- The worker and scheduler PHP processes are uid 33.
- The `release`/`operator-console` roles are one-shot `console` commands as
  `www-data`.
- The Gateway's uvicorn is uid 10001.

There is no persistent privileged process, so **#7/#8 were not blocked**.

**Removing setuid broke nothing.** Every pre-existing functional check still
passes under the hardened invocation:
- web serving;
- readiness and metrics;
- the worker/scheduler start-up;
- the production route list and config/route caching;
- the custom-PHP native smoke (TLS, MinIO, XML);
- the Gateway refusals and health.

`verify-images.sh`: **95/95**, twice in a row (82 before, plus 13
runtime-security checks).

The first hardened run found one harness timing issue, not a hardening
defect. With the database deliberately unreachable, the workers exit about
7 s after start, hardened or not; the existing "stays running" check at 5 s
was unchanged. Their process evidence is now captured in the background
while the role's PHP process runs, which keeps that check's timing exactly
as it was.

**Read-only root filesystem: not required, audited.**
- The application writes `/tmp/nginx`, `bootstrap/cache` and
  `storage/framework/views`; the Gateway writes nothing.
- A `--read-only` root with empty writable mounts fails at the application's
  `view:cache`, because the `storage` tree is missing.
- The Gateway runs read-only with a `/tmp` tmpfs.

This is recorded as a future opportunity
(`runtime-security.json` → `future_hardening`).

## 2. Exception tooling

- **Approval linkage** (`lycenza_release/exceptions.py`, schema
  `approvals` + `conditions`). Every record's `approved_by` must name an
  approval in the file. The approval's decision record must exist in the
  repository and name the reference and each advisory. A record may not go
  beyond its approval: advisory, image/package, **exact status**, the
  approved `max_days`, not before the decision date, identical conditions.
- **Conditional activation** (`verify-artifact` check `exception_conditions`).
  A `runtime-hardening` record applies only with the signed
  `verify-images.json` of the same run. That file must be bound to this
  artifact's config digest (qualify now records it), have exit code 0, and
  mark every contract-required check `PASS`. Otherwise the conditional
  records are withdrawn and verification FAILs.
- **Fix-available stop** (`evaluate.py`, the one evaluator). An exception
  never covers a HIGH that has a fix: it blocks as `high_fix_available` with
  `superseded_exception`. New advisories, versions and severities were
  already uncovered by exact matching; expiry already invalidates the file.
- **Tests:**
  - release tooling: 63 → 75, all passing;
  - PHP configuration guards: 34.
  - New release-tooling cases: approval linkage, record existence and
    content, going beyond the approval, exact per-package status, the
    approved duration, conditional records, expiry, the new-finding stop,
    the fix-available stop (any status), conditional activation with and
    without evidence (4 failure codes), and the repository file pinned to
    the owner decision.
  - A consistent libc-bin broadening, which the validator alone would
    accept, is caught by the pinned test.
- **Unchanged:** the Critical policy, the High-with-fix policy, the
  exception maximums and the verifier's other checks.
