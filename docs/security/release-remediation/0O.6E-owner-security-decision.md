## 1. Scope — exact records only

The approval covers **only** the exact exception records in
`vulnerability-exceptions.json` whose `approved_by` is `OWNER-0O6E-2026-09-26`.
Each record names one advisory, one image, one binary package and its exact
version, and the reported severity (`high`).

- There is **no family-level exception, no wildcard and no version range**.
- **No other advisory is approved.** A new HIGH or CRITICAL finding is not
  covered: it stops the release and goes to a separate review.
- The same applies to a different package version, a raised severity, or a
  newly available fix.

The release tooling enforces this (`lycenza_release.exceptions`). A record
must name an advisory listed in this approval, a package listed for its
image, and exactly that package's approved status. Its window must not exceed
the advisory's approved maximum, and it must carry the approval's conditions.

The Critical policy, the High-with-fix policy, the exception maximums (30
days for Critical/High) and the artifact verifier semantics are unchanged.

## 3. Conditions: runtime hardening (#1, #3, #4, #7, #8)

The conditional approvals depend on the production containers **not** being
able to mount filesystems or escalate privilege. Required for **both** images,
in every deployment:

1. **Not privileged:** `privileged` = false.
2. **Capabilities:** **all dropped**, none added.
3. **No new privileges:** `no-new-privileges` = true.
4. **User:** the existing non-root user (`www-data`/uid 33 for the app, `gateway`/uid 10001 for the Gateway).
5. **Setuid:** `mount`/`umount` carry **no setuid bit** (Debian `dpkg-statoverride`).
6. **fstab:** no user-mountable `/etc/fstab` entry (`user`, `users`, `owner`, `group`, `bind`, `X-mount.*`).
7. **Root processes:** no persistent privileged (root) process in any role: web, PHP-FPM, nginx, the workers, the scheduler, or the Gateway.

How this is encoded and enforced:
- **Contract:** [`infrastructure/release/runtime-security.json`](../../../infrastructure/release/runtime-security.json), a provider-neutral contract whose schema holds each safety value as a constant.
- **Proof from the kernel:** `infrastructure/docker/production/verify-images.sh` starts every container with the contract's reference invocation. It then checks `/proc/<pid>/status` for every process of every role: Uid non-root, CapPrm/CapEff/CapBnd/CapAmb zero, NoNewPrivs 1.
- **Activation gate:** `verify-artifact` applies a record with `conditions: ["runtime-hardening"]` only when the signed `verify-images.json` for **that artifact** shows every contract-required check passed. Without that evidence, the exception is withdrawn and verification FAILs.

The records are *activated* by the tooling only after this evidence exists.
Deployment evidence that the real platform applies the contract is still
outstanding (Phase 0O readiness, deployment gates). Deploying without it
breaks the condition of this approval.

**Successor rule.** Phase 0O.6F changed both images (setuid removal), and
every build gets new digests: the build time and commit are image labels. So
the approval links to a successor digest only when all of these hold:

1. The successor was built from the protected `main` commit that carries this
   record and the runtime security contract.
2. Its scan, with a fresh database, has **exactly** the reviewed residual set:
   the same 12 advisories, the same (package, version) pairs, severity `high`,
   and no fix available.
3. Its signed `verify-images.json` proves the runtime hardening.
4. `verify-artifact` returns **VERIFIED**.

Phase 0O.6F records the successor digests that met all four in
[`0O.6F-RUNTIME-HARDENING-EXCEPTIONS.md`](0O.6F-RUNTIME-HARDENING-EXCEPTIONS.md).
A later successor must meet the same four conditions. **Any** difference in
the residual set — a new advisory, a new package or version, a severity
change, or a fix becoming available — ends the approval for that finding: it
blocks and returns for a separate review.

An expired record makes the whole exception file invalid, so every
verification FAILs until the record is renewed by a new decision or removed.
Expiry is not a silent pass.

**Recheck triggers** (whichever comes first):
- the expiry date;
- any Debian 13 point or security release;
- any base-image digest refresh;
- the daily SBOM re-scan (`.github/workflows/sbom-rescan.yml`) of retained releases reporting a change;
- a finding that gains a fix, changes its affected version, or changes severity. The evaluator then blocks it: a fixed HIGH is never covered by an exception, and a changed version or severity no longer matches.
